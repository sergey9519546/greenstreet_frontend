Second DSCR Improvement Loop – 15 iterative
passes
This document records the second 15‑loop pass designed to harden every formula and algorithm in the
AEGIS‑DSCR engine. The previous round produced a high‑level improvement plan. Here each major
component is subjected to five different improvement modes:
1. Formula upgrading and hardening – refine the mathematical definitions, incorporate additional
parameters and boundary conditions, and explicitly tag all assumptions.
2. Algorithm redesign – re‑architect the computational logic where linear methods were inadequate
(e.g. discrete lender tiering) and define pseudocode for improved modules.
3. Synthetic testing – specify adversarial test cases to expose weaknesses in the old formulation and
prove the new formulation can handle those cases.
4. Edge‑case attack – identify where the component breaks down under extreme scenarios (macro
stress, irregular cash‑flows, matrix cliffs) and propose boundary checks.
5. Final canonical replacement – adopt a new formula/algorithm with an assigned implementation
priority.
Each section below corresponds to one component of the engine. For brevity, only one example adversarial
test case is shown per component, but in practice multiple tests should be coded. Pseudocode is high level
and can be translated into Python, TypeScript or any production language. Implementation priorities are
marked [High], [Medium] or [Low] relative to the engine’s critical path.
DSCR_L (Lender DSCR)
Original formula
DSCR_L = lender_accepted_rent / lender_accepted_payment
where lender_accepted_payment is defined by each lender matrix and may be PITIA (Principal +
Interest + Taxes + Insurance + Association dues) or ITIA (Interest + Taxes + Insurance + Association dues) for
interest‑only loans.
Known weakness
• Treats taxes and insurance as part of the denominator even when these appear in the numerator via
operating expenses, creating a double‑counting risk when the wrong denominator is selected.
• Fails to detect situations where high rent is offset by extraordinary expenses (management, repairs)
that are ignored in lender DSCR.

Adversarial test case
Borrower rents a house for \$3 000/month but must pay \$1 500/month in HOA and flood insurance. The lender’s
PITIA denominator is \$2 000. Under the original DSCR_L the result is 1.5x and the loan qualifies. However,
the economic DSCR_E is below 1.0x once expenses are considered. The improvement must flag this
mismatch.
Improved formula
1. Preserve DSCR_L exactly as defined by the lender matrix – do not modify its structure since it is
used solely for eligibility.
2. Add an L–E delta check:
delta_DSCR = DSCR_L - DSCR_E
if delta_DSCR > 0.2 and DSCR_E < 1.0:
flag = "Qualifies but Dangerous"
1. Introduce an adjusted lender denominator for IO loans where the lender qualifies using ITIA.
Compute Adjusted_Pmt = max(PITIA_IO, PITIA_amortizing) and compare both. Use the
larger denominator for DSCR_L when projecting beyond the IO period.
Accounting‑boundary rule
The denominator must not include taxes or insurance if these appear in the numerator’s expense
breakdown; in that case the proper denominator is Principal + Interest only. If a lender’s matrix
mandates PITIA, record a boundary violation and run the economic DSCR gate separately to avoid double
counting.
Validation test
1. Unit test: For a loan with rent \$3 000 and payment \$2 000 (PITIA) the DSCR_L should be exactly
1.5x.
2. Boundary test: For the same rent and payment when taxes and insurance are moved to the
numerator, DSCR_L should be computed on PI only and yield 3.0x. The engine should flag the
boundary mismatch.
Failure mode
If DSCR_L is used for investor survival or the numerator and denominator count the same expense, the loan may
incorrectly appear safe. Avoid using DSCR_L outside the lender ledger.

DSCR_E (Economic DSCR / Investor DSCR)
Original formula
DSCR_E = (EGI - OpEx_E) / ADS
where EGI is Effective Gross Income (rent adjusted for vacancy and collection loss) and OpEx_E includes
post‑sale taxes, insurance, HOA, management, maintenance, CapEx reserves, and other mandatory
expenses.
Known weakness
• Uses a single annual snapshot and fails to respect intra‑year cash‑flow swings; may misrepresent
seasonal or short‑term rental volatility.
• Assumes uniform expenses across time; does not reflect deferred maintenance or lumpy CapEx
events.
• Does not automatically adjust when the lender defines a different debt service structure (e.g.
interest‑only vs amortizing vs ARM resets).
Adversarial test case
Consider a mountain resort STR property with high revenue in winter and near‑zero revenue in summer. Annual
EGI is \$120 000, expenses \$60 000, ADS \$40 000 giving DSCR_E = 1.5x. However, monthly analysis reveals
four consecutive months with negative cash flow. A DSCR_E snapshot fails to capture insolvency risk.
Improved formula
1. Maintain the baseline definition but require it to be evaluated monthly as well as annually:
DSCR_E_monthly_t = (EGI_t - OpEx_t) / ADS_t
1. Define Seasonal DSCR Minimum as the minimum DSCR_E over the next 12 months and require it to
exceed a policy floor (e.g. 1.0x). If the minimum is below 1.0x for more than two consecutive months,
trigger a liquidity failure.
3

===== PAGE 4 =====

2. Incorporate dynamic debt service for ARM resets: compute ADS_t for each future period using
expected index + margin + caps.
3. Introduce egress due to CapEx events by creating a CapEx schedule and subtracting annualised
CapEx from OpEx_E only if not already included.
Accounting‑boundary rule
Do not subtract CapEx twice. If CapEx is included in OpEx_E then it must not be subtracted again when
calculating Net Cash Flow DSCR. Taxes and insurance should be subtracted once in the numerator and not
included in the denominator.
Validation test
1. Verify that monthly DSCR_E values sum to the annual DSCR_E over 12 periods (within rounding
error).
2. For a property with constant rent and expenses each month, monthly DSCR_E should equal annual
DSCR_E.
3. Test that the Seasonal DSCR Minimum triggers a flag when the lowest two consecutive months drop
below 1.0x.
Failure mode
DSCR_E may overstate safety if seasonality, CapEx, or variable debt service are ignored. Fails under variable
rate/IO loans if reset periods increase payment.
Pseudocode
def compute_dscr_e_monthly(monthly_rent_list, monthly_expense_list,
monthly_debt_service_list):
dscr_series = []
for rent, expense, debt in zip(monthly_rent_list, monthly_expense_list,
monthly_debt_service_list):
dscr_series.append((rent - expense) / debt)
seasonal_min = min(dscr_series)
return dscr_series, seasonal_min
Implementation priority: High – DSCR_E drives investor survival. Monthly analysis and seasonal minimum
are critical.
SDSCR (Stabilized DSCR)
Original formula
4

===== PAGE 5 =====

SDSCR = Stabilized_NOI / ADS
where Stabilized_NOI is the effective income minus normalised taxes, insurance, HOA, management,
maintenance, utilities and CapEx reserves.
Known weakness
• Often duplicates CapEx or management charges that are already in OpEx_E , leading to double
counting.
• Ignores a property’s actual lease terms and over‑simplifies to long‑term averages.
Adversarial test case
An industrial property has a triple‑net lease where the tenant covers taxes and insurance but not
maintenance. The original SDSCR subtracts taxes and insurance anyway and misrepresents cash flow.
Improved formula
1. Define Stabilized Expense Profile per property type and lease structure. For triple‑net, omit taxes,
insurance, and management from the numerator; for gross leases include them.
2. Use rolling averages of expenses (e.g. trailing 12 months) to estimate Stabilized_NOI rather
than fixed assumptions.
3. Subtract only future recurring expenses; do not include one‑time closing costs or initial CapEx.
Accounting‑boundary rule
If a line item is tenant‑paid, do not subtract it in Stabilized_NOI . Guarantee that each expense appears
exactly once in the equation.
Validation test
1. For a triple‑net property, SDSCR and DSCR_E should be nearly identical if the tenant covers taxes,
insurance and management.
2. Ensure that substituting a gross lease correctly lowers SDSCR due to additional expenses.
Failure mode
SDSCR fails if the underlying lease terms change mid‑projection or if property type assumptions are
misclassified.
Pseudocode
def compute_sdscr(stabilized_noi, annual_debt_service):
return stabilized_noi / annual_debt_service

RWDSCR (Robust Worst‑Case DSCR)
Original formula
RWDSCR = min(Base_DSCR_E, Tax_Shock_DSCR, Insurance_Shock_DSCR,
Vacancy_Shock_DSCR,
CapEx_Stress_DSCR, Reset_Safe_DSCR, Combined_Stress_DSCR)
Known weakness
• Does not account for correlated macro scenarios (e.g. stagflation vs recession) and may double
count or omit interacting factors.
• The minimum operator can over‑penalise if one shock is extremely severe but improbable; there is
no weighting by likelihood.
Adversarial test case
During a hurricane season, insurance premiums spike 80% and property taxes are reassessed. The original
RWDSCR takes the minimum of Insurance_Shock_DSCR and Tax_Shock_DSCR separately but fails to combine
them with vacancy losses from evacuation. The true worst case is worse than either individual shock.
Improved formula
1. Replace the simple minimum with a scenario library of named correlated shocks (e.g.
Stagflation , Recession , Climate Event , Local Distress ). Compute DSCR under each
and take the worst result:
RWDSCR = min(DSCR_stagflation, DSCR_recession, DSCR_climate_event,
DSCR_local_distress)
1. Within each scenario, apply correlated shocks across rent, vacancy, expenses, debt service, cap rate
and refi assumptions.
2. Introduce an optional probability‑weighted RWDSCR for internal analysis (not gating), allowing
management to view expected shortfall relative to probability of occurrence. Do not use for approval
to avoid black‑box decisions.
Accounting‑boundary rule
Every shock must be applied to either numerator or denominator but not both. Ensure correlated scenarios
do not double count the same input (e.g. do not raise both insurance and debt service if the increased rate
is already captured in interest shock).
6

Validation test
1. Validate that RWDSCR under a Climate Event scenario is lower than or equal to the individual
Insurance and Tax Shock DSCR if those shocks are combined with vacancy losses.
2. Check that RWDSCR never exceeds DSCR_E .
Failure mode
If correlation patterns are mis‑specified (e.g. combining tax reassessment with rent growth), RWDSCR may
be overly punitive or overly optimistic. Scenario definitions must be continually calibrated to market data.
Pseudocode
def compute_rwdscr(dscr_scenarios):
return min(dscr_scenarios.values())
Implementation priority: High – RWDSCR is critical for stress gating.
Tax Shock DSCR
Original formula
Tax_Shock_DSCR = (Stabilized_NOI - ΔTax) / ADS
where ΔTax = max(0, projected_post_sale_taxes - current_taxes).
Known weakness
• Assumes one‑time jump but not incremental tax rises over time.
• Ignores homestead exemptions, capped reassessment laws and special tax districts.
Adversarial test case
In Texas, property tax is capped at 10% per year but reappraisal occurs every three years. A property
purchased at \$1 000 000 with a previous assessed value of \$500 000 would not see a full doubling of taxes
in year one; the shock would be phased in. The original formula wrongly subtracts the entire delta
immediately.
Improved formula
1. Include jurisdictional tax rules – step caps, reassessment cycles and exemptions – in the tax
projection. When the cap is 10% per year, compute ΔTax_year1 = min(0.1 * current_taxes,
ΔTax_total) , etc.
7

===== PAGE 8 =====

2. Spread tax shock over the reassessment schedule. If the full delta cannot occur in one year, adjust
DSCR calculation accordingly.
3. Permit user override with verified tax estimate (e.g. from county assessor or title company).
Accounting‑boundary rule
Subtract only the incremental tax above current taxes; do not subtract full new tax bill if part of it is already
included in OpEx_E .
Validation test
1. For a state with no caps, full tax shock subtraction should match ΔTax .
2. In a capped jurisdiction, ensure tax increases are phased and DSCR improves in early years.
Failure mode
Misclassifying tax rules leads to over‑ or under‑estimating DSCR. Fails if user inputs outdated tax rates.
Pseudocode
def compute_tax_shock_dscr(stabilized_noi, ads, tax_projection, current_taxes):
delta_tax = max(0, tax_projection - current_taxes)
return (stabilized_noi - delta_tax) / ads
Implementation priority: Medium – critical for certain markets; must integrate local data sources.
Insurance Shock DSCR
Original formula
Insurance_Shock_DSCR = (Stabilized_NOI - ΔInsurance) / ADS
where ΔInsurance = Current_Insurance × Shock_% .
Known weakness
• Uses a flat shock percentage that may not reflect actual insurance pricing by region or property type.
• Ignores the difference between hazard insurance (structure) and liability or umbrella policies.
Adversarial test case
In Florida, insurance increases may exceed 200% after a hurricane season, while other regions see minimal
change. A flat 25% shock underestimates risk in high‑risk regions and overstates risk elsewhere.
8

===== PAGE 9 =====

Improved formula
1. Pull region‑specific insurance indices (e.g. from state insurance regulators, FEMA hazard zones) to
calibrate the shock percentage. For high‑risk zones, set shock to 50‑200%; for low‑risk zones, set
shock to 10–20%.
2. Separate structure insurance from liability/umbrella in the expense breakdown. Shock only the
structure portion subject to hazard risk. Do not double count liability policies.
Accounting‑boundary rule
Subtract only the increased portion of insurance; do not subtract the full insurance premium twice.
Validation test
1. For a Florida rental property, test insurance shock DSCR using a 150% increase and verify DSCR
declines appropriately.
2. For a Midwestern property, test a 10% shock and confirm DSCR is minimally affected.
Failure mode
Fails when inaccurate hazard zoning or misclassified property type mis‑calibrates the shock.
Pseudocode
def compute_insurance_shock_dscr(stabilized_noi, ads, current_insurance,
shock_percent):
delta_insurance = current_insurance * shock_percent
return (stabilized_noi - delta_insurance) / ads
Implementation priority: Medium – dependent on data quality; integrate hazard risk models gradually.
Vacancy Shock DSCR and Break‑Even Vacancy
Original formulas
Vacancy Shock DSCR
DSCR_V = [GSI × (1 − v_shock) − OpEx_fixed − variable OpEx] / ADS
Break‑Even Vacancy
9

===== PAGE 10 =====

v_BE = 1 − (ADS + OpEx_fixed) / [GSI × (1 − management_rate)]
Known weakness
• Assumes linear relationship between vacancy and variable expenses; management may not scale
linearly for small properties.
• Break‑Even formula fails when GSI is extremely low or negative, causing division by near‑zero and
meaningless results.
Adversarial test case
A duplex with GSI = \$24 000 , ADS + fixed OpEx = \$22 000 , management fee = 8%. v_BE
becomes negative (structurally impossible), indicating that even 100% occupancy cannot cover fixed costs.
The original formula returns v_BE > 1 , causing misinterpretation.
Improved formula
1. Add guard clause: if (ADS + OpEx_fixed) ≥ GSI , set v_BE = 0 and flag the property as
structurally cash‑negative. A negative break‑even vacancy means the deal is impossible without
repairs or equity injection.
2. Calibrate management scaling – for small properties (1–4 units), treat management as fixed per
unit and adjust the variable component accordingly.
3. For Vacancy Shock DSCR, shock only the revenue side; leave fixed expenses unchanged but scale
variable expenses (e.g. utilities, maintenance) proportionally to occupancy.
Accounting‑boundary rule
Ensure ADS + OpEx_fixed is not subtracted from GSI if those expenses are already included in the
numerator for other DSCR variants.
Validation test
1. For the duplex example, the guard clause should trigger and v_BE should be set to 0 with a
structural failure flag.
2. For a large multi‑unit property, verify that v_BE falls between 0 and 1 and scales with
management_rate .
Failure mode
Break‑Even formulas fail when GSI is unverified or drastically overestimated, or when management
structure is misclassified.
Pseudocode

def compute_break_even_vacancy(gsi, ads, fixed_op_ex, management_rate):
if gsi <= ads + fixed_op_ex:
return 0.0 # structural failure
numerator = ads + fixed_op_ex
denominator = gsi * (1 - management_rate)
return 1 - numerator / denominator
Implementation priority: High – break‑even metrics guard against unrealistic occupancy assumptions.
CapEx Stress DSCR
Original formula
DSCR_CapEx = [Stabilized_NOI - annualised_capex_event] / ADS
where annualised_capex_event is a large, one‑off repair cost divided over a single year to simulate its
impact.
Known weakness
• Annualising an event could underestimate the shock if it happens mid‑year (e.g. a \$50 000 roof
replacement at once).
• Does not factor in whether reserves are available to absorb the event.
Adversarial test case
A \$200 000 HVAC replacement occurs in month 2 of the year and there are only \$80 000 in reserves.
Annualising to \$200 000/12 = \$16 667 monthly does not reflect the early cash hit and resulting liquidity
failure.
Improved formula
1. Use the Sequential Drawdown Array to model CapEx events at their actual timing and compare the
resulting cash balance vs reserves. DSCR_CapEx becomes a by‑product of the drawdown rather than
a separate static ratio.
2. If using an annualised approach for screening, require that reserves ≥ one full CapEx event; if not,
trigger a liquidity failure.
3. Distinguish between planned CapEx (age‑based schedule) and unplanned CapEx (random shock).
Use distributional assumptions for unplanned events but only for internal risk metrics, not gating.
Accounting‑boundary rule
11

===== PAGE 12 =====

Ensure that CapEx is not subtracted both in OpEx_E and again in the stress test. Track CapEx in a separate
account.
Validation test
1. In the adversarial case, the sequential drawdown should show negative cash in month 2 and trigger
a failure, despite DSCR_CapEx > 1 using annualisation.
2. Verify that annualised CapEx DSCR approximates the effect of multiple small repairs evenly spaced.
Failure mode
Fails if the schedule of CapEx events is mis‑estimated or if reserves are misreported.
Pseudocode
def sequential_capex_stress(noi_series, capex_events, ads_series,
starting_reserves):
cash_balance = starting_reserves
for t in range(len(noi_series)):
cash_balance += noi_series[t] - ads_series[t]
if t in capex_events:
cash_balance -= capex_events[t]
if cash_balance < 0:
return False # liquidity failure
return True # survives
Implementation priority: High – CapEx stress ties into liquidity and reserve adequacy.
LSC (Liquidity Survival Clock)
Original formula
LSC = Verified_Reserves / Monthly_Cash_Drain
where Monthly_Cash_Drain is PITIA + fixed operating expenses (taxes, insurance, HOA, management,
maintenance, CapEx reserves) under a zero‑income scenario.
Known weakness
• Does not account for variable expenses that may still occur during vacancy or STR off‑season.
• Fails to model the timing of draws and could misclassify survival length if expenses are lumpy.
Adversarial test case
12

===== PAGE 13 =====

Reserves of \$40 000 with monthly cash drain of \$5 000 suggest an LSC of 8 months. However, an
unexpected \$15 000 repair in month 2 wipes out reserves and bankrupts the borrower. The scalar LSC
missed this path dependency.
Improved formula
1. Use Sequential Drawdown Array to replace the scalar LSC for gating. LSC remains a quick
diagnostic but not a decision driver.
2. Incorporate variable expenses into the denominator (e.g. minimal maintenance, utilities) even
when there is no income.
3. Introduce Emergency Liquidity Cushion equal to at least one month’s cash drain on top of the base
reserves.
Accounting‑boundary rule
Ensure that the cash drain includes only expenses not recovered from tenants (tenant‑paid utilities are
excluded). Use PI in the denominator if taxes and insurance are subtracted in the numerator.
Validation test
1. Ensure that the sequential drawdown result contradicts the scalar LSC in the adversarial case.
2. For a property with uniform monthly expenses, scalar and sequential LSC should agree.
Failure mode
LSC fails if reserves are over‑reported or if expenses are misclassified as tenant‑paid. Scalar LSC cannot
detect early shocks.
Pseudocode
def compute_lsc(reserves, monthly_cash_drain):
return reserves / monthly_cash_drain
def sequential_drawdown(noi_series, expense_series, ads_series, reserves):
balance = reserves
for t in range(len(noi_series)):
balance += noi_series[t] - ads_series[t] - expense_series[t]
if balance < 0:
return False
return True
Implementation priority: High – liquidity determines survival.

Sequential Drawdown
Original algorithm
Simulates monthly cash flow over a projection horizon to see if reserves ever drop below zero. Uses monthly
NOI (income minus operating expenses), monthly debt service and scheduled CapEx events.
Known weakness
• May exclude seasonality or STR troughs from the income series and thus underestimate negative
cash flows.
• Fails to incorporate adjustable debt service (ARM resets) and balloon payments.
Adversarial test case
STR property with revenue curve [12000, 10000, 8000, 5000, 3000, 1000, 1000, 1000, 3000,
5000, 8000, 10000] and monthly expenses \$6 000, debt service \$4 000. Reserves are \$20 000. At
month 7, the cash balance becomes negative due to low rent. The algorithm must detect this.
Improved algorithm
1. Include seasonality – supply monthly rent projections using the Seasonality Trough Detector or
custom curves.
2. Incorporate debt service resets – compute monthly debt service using the expected interest rate
path (fixed, ARM, or reset schedule).
3. Inject scheduled CapEx events – subtract large repairs at their actual month.
4. If the cash balance drops below zero at any point, set Liquidity Failure = True and flag the deal.
Accounting‑boundary rule
Do not subtract taxes and insurance in both the monthly expense series and the debt service; use PI for
debt and include taxes in the expense series if applicable.
Validation test
1. Ensure the sequential drawdown replicates the scalar LSC for flat income/expense series.
2. Test the STR curve example; confirm the drawdown fails in month 7 even though the annual DSCR
appears strong.
Failure mode
Fails if monthly income and expense forecasts are inaccurate, or if CapEx and resets are mis‑timed. The
model can over‑penalise if improbable shocks are assumed.
Pseudocode
14

===== PAGE 15 =====

def sequential_drawdown(noi_series, debt_service_series, capex_events,
starting_reserves):
balance = starting_reserves
for t in range(len(noi_series)):
balance += noi_series[t] - debt_service_series[t]
if t in capex_events:
balance -= capex_events[t]
if balance < 0:
return False
return True
Implementation priority: High – drives liquidity survival tests.
Seasonality Trough / Maximum Cumulative Intra‑Year Deficit
(MCID)
Original algorithm
Computes DSCR_E on an annual basis or at best monthly but does not explicitly measure the maximum
cash deficit during seasonal low periods.
Known weakness
• Fails to calculate cumulative losses across consecutive low‑income months (e.g. winter slump in
seasonal markets).
• Does not adjust the required reserves to cover the trough.
Adversarial test case
A student housing property collects 90% of its rent in nine months and 10% across the remaining three.
During the summer recess, the property operates at a loss of \$4 000 per month for three months. Without
sufficient reserves, the investor fails despite a high annual DSCR.
Improved algorithm
1. Compute MCID – simulate monthly net cash flow and track the maximum negative cumulative
sum from any starting month within a 12‑month window. This value indicates how much reserve is
needed to survive the worst intra‑year slump.
2. Add a Seasonality Reserve Requirement equal to MCID. If verified reserves are less than MCID, flag
the property as failing the seasonality trough test.
3. Provide a summary metric: Seasonal DSCR Minimum (lowest DSCR_E_monthly), MCID, and required
reserves.
Accounting‑boundary rule
15

===== PAGE 16 =====

Ensure that MCID uses monthly net cash flow after all expenses and debt service, consistent with
sequential drawdown logic.
Validation test
1. For the student housing case, MCID should equal \$12 000 (\$4 000 × 3 months) and require at least
that amount in reserves.
2. For a property with flat cash flow, MCID should be zero.
Failure mode
Mis‑estimating monthly income or ignoring variable expenses can miscalculate the MCID. The test fails if
MCID is not recalculated for extended leases or major tenant turnover.
Pseudocode
def compute_mcid(monthly_net_cashflow):
cumulative = 0
min_cumulative = 0
for cash in monthly_net_cashflow:
cumulative += cash
if cumulative < min_cumulative:
min_cumulative = cumulative
return abs(min_cumulative)
Implementation priority: High – essential for STR/student housing deals.
IO Reset Cliff
Original algorithm
Compares DSCR during interest‑only period to DSCR when amortization begins; sometimes uses a simple
“payment increase” percentage as a warning.
Known weakness
• Does not incorporate principal balance after the IO period; if the loan has negative or partial
amortization, the reset payment may be higher than a standard amortizing payment.
• Fails to account for potential rate changes on ARM/IO hybrid products.
Adversarial test case
16

===== PAGE 17 =====

Borrower obtains a 7‑year IO loan with a balloon in year 7. Payment is \$3 000 monthly during IO, but the
refi reset payment at a higher rate jumps to \$7 000. DSCR drops from 1.5x to 0.6x. The original algorithm
may not catch this if it only looks at a moderate increase percentage.
Improved algorithm
1. Compute Reset DSCR using the remaining amortization period and forecast rate at the reset point:
reset_payment = pmt(remaining_balance, forecast_rate, remaining_term)
reset_dscr = (stabilized_noi_at_reset) / (reset_payment * 12)
1. Define Cliff Ratio = DSCR_IO / reset_dscr and Payment Shock = (reset_payment -
IO_payment)/IO_payment .
2. Require reset_dscr ≥ policy_dscr_min (e.g. 1.0x). If not, trigger an IO reset failure.
3. Adjust for ARM rate index if the reset rate is variable; compute worst‑case rate using fully indexed
rate + lifetime cap.
Accounting‑boundary rule
Use P&I payment for reset; do not include taxes/insurance/HOA since those remain constant or already in
the numerator.
Validation test
1. For the adversarial case, verify that reset_dscr = 0.6x and triggers failure.
2. For a fixed‑rate IO loan converting to amortizing at the same rate, ensure payment shock is
computed correctly and no unwarranted failure occurs.
Failure mode
Fails if forecast rates are underestimated or if the remaining balance is miscalculated due to prepayment or
partial amortization.
Pseudocode
def compute_io_reset_cliff(loan_balance, io_payment, forecast_rate,
remaining_term, stabilized_noi):
reset_payment = pmt(loan_balance, forecast_rate, remaining_term)
reset_dscr = stabilized_noi / (reset_payment * 12)
cliff_ratio = (stabilized_noi / (io_payment * 12)) / reset_dscr
return reset_dscr, cliff_ratio
Implementation priority: High – IO reset failure is a major risk for DSCR loans.

ARM Reset
Original algorithm
Handles adjustable‑rate mortgages by using a static rate increase (e.g. +200 bps) or ignoring resets
altogether.
Known weakness
• Does not respect rate caps, floors, or periodic limits. May under‑ or over‑estimate payment changes.

Original algorithm
Projected value at refi was assumed constant. Cap rate changes were ignored.
Known weakness

4. Alerting – produce reports when metrics exceed thresholds (e.g. DSCR miss rate > 5%, distribution
drift > 10%).
Accounting‑boundary rule
Ensure that outcome data is anonymised and aggregated to protect PII. Use only for performance
monitoring, not for predictive scoring beyond the model’s scope.
Validation test
1. Inject a known drift (simulate rent dropping by 20% across a portfolio) and verify that the drift
monitor flags the shift.
2. Use a backtest set; confirm that the backtest system replicates historical decisions and identifies
differences when models are updated.
Failure mode
Monitoring fails if outcome data is delayed, misreported or incomplete. Calibration can be biased if the
sample is not representative.
